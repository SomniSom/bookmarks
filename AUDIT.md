## 2. Сводка

Проект небольшой (2748 строк Go в 9 файлах) и в целом аккуратный: современный
`net/http.ServeMux` с методами и `PathValue`, `CGO_ENABLED=0`, статическая сборка, scratch-образ,
`embed` для шаблонов и статики. Реальных блокеров два: **нулевое покрытие тестами** и
**неатомарный импорт с заменой данных**. Остальное — гигиена (линтеры, CI, версии),
безопасность (нет таймаутов сервера, нет анти-SSRF, нет ограничения попыток входа) и
оптимизации, часть из которых подтверждена замерами.

Ключевая цифра: **0 тестов, 0.0% покрытия**. Заявленные в README возможности (дерево, корзина,
импорт, бэкапы, проверка ссылок) не проверяются ничем, а CI (`.github/workflows/image.yml`)
собирает образ без единого теста — только `go vet` и сборка.

## 3. Проблемы по категориям

### 3.1 Дефекты логики

1. **Неатомарный импорт с заменой** — `internal/store/store.go:1210-1233`.
   При `replace=true` транзакция удаляет `node_tags` и `nodes` и **коммитится до импорта**
   (`tx.Commit()` на строке 1224), а сам импорт идёт вне транзакции через `importOne → CreateNode`.
   Любая ошибка на середине (или падение процесса) оставляет базу полупустой. Таблица `tags`
   при этом не чистится — остаются осиротевшие теги. Импорт 2000 закладок делает 2000 отдельных
   коммитов WAL.
2. **Мёртвая тяжёлая загрузка** — `internal/store/store.go:689-715`. `descendantIDs` вызывает
   `LiveNodes()` (два запроса + сборка карты всех узлов, замерено 19.3 мс на 2050 узлах),
   затем результат выбрасывает (`_ = list`). Вызывается из `SoftDelete`, `Restore`, `Purge`.
3. **N+1 при построении путей** — `store.go:358, 835, 860, 897`. `PathFor` делает по одному
   `SELECT` на каждый уровень вложенности; в `Search` (до 50 результатов), `TrashRoots`,
   `Duplicates` вызывается в цикле. 33.7 мкс на узел, растёт линейно.
4. **Ошибки рендера шаблонов игнорируются** — `internal/server/server.go:279, 314, 319, 324`
   (`_ = s.tplX.Execute(...)`). При ошибке клиент получает 200 и обрезанную страницу.
5. **Неэффективное присваивание** — `store.go:751` (`parent = nil`, значение не используется),
   ловится `ineffassign`.
6. **Мёртвый код** — `store.ErrHasPassword` (`store.go:23`) нигде не возвращается и не проверяется.
7. **`go vet`/`gofmt`**: `internal/store/store.go` не отформатирован (следствие ручной правки
   выравнивания var-блока).
8. Защита от циклов в `parentChainContains` (`store.go:451-468`) при обнаружении цикла считает
   узел «содержащим» и молча поднимает его в корень — данные не теряются, но диагностики нет.

### 3.2 Безопасность

1. **Нет таймаутов HTTP-сервера** — `cmd/bookmarks/main.go:33` использует `http.ListenAndServe`
   без `ReadHeaderTimeout`/`ReadTimeout`/`IdleTimeout` → slowloris и удержание соединений.
   Нет graceful shutdown: SIGTERM (docker stop) обрывает запросы и фоновой бэкап.
2. **SSRF в OG-фетче и проверке ссылок** — `internal/og/og.go:36`, `internal/links/links.go:101`.
   URL приходит от пользователя, редиректы следуют до 8 раз, приватные диапазоны
   (`127.0.0.0/8`, `10/8`, `192.168/16`, `169.254.169.254`, `::1`) не блокируются. Приложение
   однопользовательское, но живёт в контейнере с сетью — фильтр нужен.
3. **Нет ограничения попыток входа** — `POST /login` (`server.go:282`) вызывает argon2id с
   `m=64MB, t=3` без задержек и счётчиков → любой может нагружать CPU/память параллельными
   запросами.
4. **CORS по префиксу origin** — `server.go:139-155` + `auth.IsExtensionOrigin` разрешает любой
   `chrome-extension://*` и `moz-extension://*`. При `require_extension_auth=0` любое расширение
   браузера получает полный доступ к API.
5. **`X-Forwarded-Proto` учитывается всегда** — `server.go:185`, независимо от `TRUSTED_PROXY`;
   флаг Secure у cookie ставится по непроверенному заголовку.
6. **Нет заголовков безопасности** (`X-Content-Type-Options`, `Referrer-Policy`, CSP),
   нет HSTS при работе за прокси.
7. Плюсы, которые стоит сохранить: пароли только в виде argon2id-хеша, токены сессий хранятся
   хешами SHA-256, cookie подписана HMAC, `SameSite=Lax` + JSON-тела запросов дают базовую
   защиту от CSRF, `.env` не в индексе git (отслеживается только `.env.example`).

## 5. Что оптимизировать (по приоритету, с ожидаемым эффектом)

1. **Транзакции на батч-записи**: `SetNodeTags`, `reorderSiblings` (N `UPDATE` по одному),
   `SoftDelete`/`Restore`/`Purge`, `EmptyTrash`, `ImportBrowser`, `ImportJSON`. Один
   `Begin/Commit` + prepared statements. Ожидаемо: импорт 2000 закладок с ~1 с до ~100 мс.
2. **Убрать `LiveNodes()` в `descendantIDs`** — минус 19 мс на каждое удаление/восстановление
   при 2k узлов.
3. **Убрать N+1 в `PathFor`** — рекурсивный CTE (`WITH RECURSIVE`) одним запросом либо сборка
   путей из уже загруженного набора в `Search`/`TrashRoots`/`Duplicates`. Минус ~1.7 мс на поиск,
   и перестаёт зависеть от глубины.
4. **Кэш дерева в памяти с версией** (инвалидация на всех путях записи) или ETag:
   `GET /api/tree` 23 мс → <1 мс при попадании. Дерево меняется только через API этого процесса.
5. **Один общий `http.Client`/`http.Transport`** для `og.Fetch` и `links.probe` вместо
   создания клиента на каждый вызов (сейчас `CheckAll` на 2000 ссылок создаёт 2000 транспортов,
   теряя keep-alive и делая TLS-хендшейк на каждую ссылку). Плюс лимиты `MaxIdleConnsPerHost`.
6. **Асинхронный OG-фетч**: `POST /api/nodes` сейчас ждёт до 8 с (`og.Fetch`) перед ответом.
   Возвращать 201 сразу, OG догружать фоном (endpoint `POST /api/nodes/{id}/og` уже есть).
7. **FTS5 на поиск**: `LIKE '%q%'` с `COLLATE NOCASE` по трём полям и `DISTINCT` через join
   деградирует линейно; при росте базы заменить на виртуальную таблицу FTS5 с триггерами.
8. **Контексты в SQL** (`noctx`, 13 мест): проброс `r.Context()` даёт отмену при отключении
   клиента и таймауты — заодно закрывает замечания линтера.
9. **Настройки SQLite**: сейчас `busy_timeout=5000`, `foreign_keys=1`, WAL, `MaxOpenConns(1)`.
   Добавить `synchronous(NORMAL)` (безопасно при WAL, меньше fsync), оценить `cache_size`
   и отдельный пул на чтение при сохранении одного писателя.
10. **HTTP**: `http.Server` с таймаутами, gzip для JSON (дерево на 2k узлов — сотни КБ),
    `Cache-Control`/ETag для `/static/` (сейчас `http.FileServer` отдаёт embed-файлы без кэша),
    `http.FileServerFS` вместо `fs.Sub`+`FileServer`.
11. **PGO**: снять профиль на живом инстансе (`pprof`), положить `default.pgo`, собирать
    `-pgo=auto` — обычно 2-7% CPU на горячих путях. Делать после стабилизации бенчмарков.
12. Мелочи: преаллокация в `LiveNodes`/`PathFor`, `strings.Builder` в `PathFor`,
    два вызова `fmtTime(now())` в `UpdateLink` (`store.go:589-601`).

## 8. Риски

- **Подъём Go 1.24 → 1.27** сразу на три минорные версии: совместимость гарантируется, но без
  тестов регрессии не видны. Смягчение: сначала минимальные тесты на `store`/`server` (часть
  этапа 4) или прогон на копии БД; CI собирает образ на новой версии до мержа.
- **Обновление `modernc.org/sqlite`** (v1.40 → v1.61) может изменить поведение pragma/DSN.
  Смягчение: миграция и бэкап проверяются на копии реальной базы, тест открытия существующей БД.
- **Кэш дерева** — риск рассинхронизации; инвалидация на всех путях записи + тест
  «запись → чтение видит изменение».
- **Anti-SSRF** может отсечь легитимные локальные адреса (домашние сервисы в закладках) —
  нужен явный конфиг-allowlist или флаг.
- **PGO** даёт смысл только на реальном профиле; без стабильных бенчмарков измерить эффект нельзя.

## 9. Что делать не нужно

- Переход на `mattn/go-sqlite3` ради скорости: ломает `CGO_ENABLED=0` и scratch-образ.
- Замена `net/http` на роутер-фреймворк: `ServeMux` с методами и `PathValue` покрывает всё.
- Кэширование статики «на глаз»: сначала `ETag`/`Cache-Control`, замер — потом.

### Отклонения от плана

- **Асинхронный OG-фетч не включён.** `POST /api/nodes` по-прежнему ждёт OG: фронтенд
  показывает карточку сразу после создания, и фоновая догрузка дала бы пустую карточку без
  доработки поллинга на клиенте. Изменение отложено до появления такой доработки.
- **CORS оставлен по префиксу origin** (`chrome-extension://`, `moz-extension://`):
  идентификаторы расширений при установке «распакованным» неизвестны заранее, allowlist
  сломал бы установку. Компенсация — `require_extension_auth=1` по умолчанию.
- **`DELETE /api/nodes/{id}` и purge для несуществующего узла отвечают 200** — сознательная
  идемпотентность; `404` отдаёт только `GET`.
- **`PATCH /api/nodes/{id}` неатомарен**: при недопустимом `parentId` ответ 400, но
  title/url/notes/tags уже записаны. Требует объединения в одну транзакцию store — вынесено
  в отдельную задачу, чтобы не менять публичный API `store` в этом проходе.
- **PGO не добавлен**: профиль реальной нагрузки не снимался, без него эффект не измерить.
